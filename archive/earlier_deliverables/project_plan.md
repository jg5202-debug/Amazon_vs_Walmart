# Retail Growth and Profitability Comparison

本项目采用 Jupyter Notebook 和四个模块。每个模块提供英文标题、以英文注释开头的 code cells，以及中文说明与完整英文代码合在一起的 guide。

## 代码写法约定

优先使用普通函数、简单类、字典、列表、`for` 循环和 `if` 判断。首版避免装饰器、复杂类型标注、过度继承和 ORM。需要对象保存状态或提供稳定接口时才使用类，使用明确的 `__init__` 与常规方法。

Module 01 使用一个简单 `StudyConfig` 类；内容来自普通字典，JSON 读写使用 `save_study_config` 和 `load_study_config` 两个普通函数。代码中的命名、注释与输出保持英文，guide 逐格用中文解释作用。

每个模块的 guide 还需详细解释每个代码段和函数：先交代构建思路，再说明输入、输出、调用时机、主要语句的含义以及为什么选用这一写法。较长方法按职责拆段讲解；明确区分 Python 语法、项目选择的规则和研究方法限制。说明与完整代码合在同一 guide 中，并同步到 Notebook 的中文 Markdown cells。

## 研究范围

比较 Amazon North America 与 Walmart U.S. 的销售增长和营业盈利能力。分析年度为 2019—2024，对应 Amazon 2019—2024 与 Walmart FY2020—FY2025，共 12 个分部年度观察值。2019 正式纳入比较，作为疫情前参照年和销售指数基期。财年近似配对，实际起止日期仍需核对。

基础数据为分部净销售额和营业利润。销售增长率、营业利润率、销售指数均由基础数据计算，而非依赖不同网站给出的现成比率。2019 年同比因未采集 2018 基线而留空，2020—2024 年同比使用各分部自己的上年销售额。基期指数为 100，不代表基期同比增长率为零。

## Module 01: Research Configuration

负责研究对象、指标、年份、财年配对、描述性比较阶段、来源、导入文件和数据库路径。阶段标签通过每个 `period` 的可选 `comparison_stage` 字段传递；更换内容时调整标签，通用类不硬编码疫情分期。输出 `config` 对象与 `study.json`。内容集中在配置中，通用代码不判断特定公司名称。

数据库位置使用 `database_file`，默认为 `../data/retail_comparison.sqlite`，相对于配置文件解析。第一模块只解析和显示路径，不创建数据库。

## Module 02: Data and Database Management

负责从免费官方财报收集或导入基础数据，核对分部、日期、币种、单位、重复记录和来源，然后将通过检查的标准数据写入 SQLite 数据库。

步骤为：收集所需数据 → 保留原始导入材料 → 标准化并检查 → 创建数据库结构 → 导入已验证记录 → 查询回读核对。

采用 SQLite，因为当前是个人本地、小样本分析，数据库可以保存为一个文件，不需要部署独立服务。通过 Python 的 `sqlite3` 接口访问。[SQLite 官方适用场景](https://www.sqlite.org/whentouse.html)、[Python sqlite3 文档](https://docs.python.org/3/library/sqlite3.html)

OOP 中由 `DatabaseManager` 封装连接、建表、写入和查询。数据管理模块负责数据检查，数据库访问对象负责存取；计算模块和报告模块通过这个对象访问数据，不到处复制 SQL。

CSV 是导入及核对材料；数据库是后续分析的数据入口。保留官方来源链接、财报标识及页码或章节，让每一个基础数值可以追溯。项目采集只使用免费公开财报；数据库不会补全财报未披露的内容。

## Module 03: Metrics and Comparative Analysis

按 `config` 选择研究对象和年份，通过数据库访问对象查询标准财务记录，计算销售增长率、营业利润率和以 2019=100 的销售指数，按配置标签组织疫情前参照、冲击期和后续调整期的比较结果，再保存指标结果。基础指标仍为三个，不增加复杂模型。

指标计算对象不依赖 SQLite，也不包含特定公司名称；它接收统一的财务记录。更换来源或存储方式不改变指标公式。

数据库中的基础数据与计算结果分别保存。基期、研究配置或基础数据变化后，重新计算对应指标；不能直接复用旧结果。缺失指标保存为 NULL，并标注原因，不填零。负营业利润是合法数据。

## Module 04: Reporting and Workflow

负责串联配置、数据管理、指标计算和展示。读取与当前配置对应的记录及结果，输出销售指数图、营业利润率图、结果表、解释和来源。图上标出 2019 基期及 2020—2021、2022—2024 两个比较阶段，并在报告中解释相对 2019 的变化。

报告模板规定结构，配置提供题目和对象名称，分析对象提供数值。年报解释与计算结果分开记录，保持描述性比较，不将时间上的共同变化写成已经证实的因果关系。

## 计划中的数据库结构

三张核心表已在第二模块建立，完整 SQL 与约束见 module_02/data_management.py 及 guide。数据库已保存真实基础记录，第三模块已计算并验证当前签名的 36 条指标结果，其中两条首年同比为 NULL。

### business_units

记录 `unit_id`、公司名称、股票代码、分部名称和口径说明。用于标识研究对象，不用公司显示名称作为数据匹配依据。

### financial_records

每行代表一个分部的一个报告年度，记录 `unit_id`、报告财年、实际起止日期、净销售额、营业利润、币种、金额单位及来源定位。记录该次采用的原始披露值及标准化值，保留单位转换依据。

正式研究目前需要 12 条年度记录。重复导入同一记录不得产生重复行；若财报数值重述，需要明确采用的版本并重新计算相关结果。原始材料保留用于核对。

实际报告期间属于基础数据；把该期间配到哪个分析年度属于研究配置，不将某一次研究的财年配对永久写死在基础数据中。

### metric_results

每行保存一个研究对象在某分析年度的某项指标，包括 `study_id`、配置签名、`unit_id`、分析年度、指标名称、数值、计算时间及必要的缺失说明。销售指数结果应能识别采用的基期；配置签名或保存的配置快照用于区分不同研究设置。

这张表在第二模块规划和建表，由第三模块计算后填充。第一模块输出的 JSON 保留作为研究设置文件，指标结果需要能够对应到生成它的配置。

## 疫情前后比较的研究动机与安排

加入 2019，是为了给疫情期间及后续变化提供疫情前参照，而不只是增加一个年份。研究问题为：相对 2019 年的销售规模和营业利润率，两个分部在 2020—2021 年及 2022—2024 年分别发生了怎样的变化，其变化路径有何不同？

- **2019：疫情前参照（Pre-pandemic baseline）**。销售指数以该年为 100，营业利润率用于后续水平比较。
- **2020—2021：疫情冲击阶段（Pandemic disruption）**。查看销售增长是否伴随利润率改善，并比较两个分部的变化。
- **2022—2024：后续调整阶段（Subsequent adjustment）**。查看增长放缓或延续、利润率回落或恢复等现象。该标签是项目的操作性划分，不认定疫情在 2022 年已经结束。

阶段归属按共同分析年度确定，再映射到各分部真实财年；财年不完全一致。报告保留年度结果，不将一个年份的基线与两年或三年的汇总数直接混比。可补充阶段平均利润率并明确年数与计算方法；利润率变化用百分点，销售指数变化用指数点。

本项目仍是小样本的描述性比较。只有一个疫情前年份，无法检查疫情前趋势；两家分部的业务构成也不同，因此不能把全部变化归因于疫情，不采用因果估计或显著性检验。

流程图与具体数据管道见 `diagram_guide.md` 和 `diagrams/`。图中的来源值已转录到真实 CSV 并通过 Module 02 入库；指标计算、阶段汇总、图表与报告均已实现。未附完整官方 HTML 快照，来源清单、官方链接和转录证据已保留，完整报表可按需通过浏览器另行保存。
